## D-007 · 2026-11-09 · 批量上传 = 一次提交多个资源，全局单并发串行跑

- 原：一次提交就是一个资源（`POST /api/upload` 只收单个 `file`，返回 `{title, items, failed}`，进度板 `job.pans` 扁平），批量只能一个个点上传，几十个资源要点几十次；拖文件夹更是静默无反应
- 现：一次提交可带多个文件与它们的相对路径（`files` + `paths`）。**每个顶层目录 = 一个资源**，各自建以自己名字命名的网盘文件夹、各自分享链接、飞书各写一节；没有目录的一批散文件合成一个资源（用表单标题命名）。返回从「一条结果」变为 `{batch_id, count, resources:[…]}`，进度从「一个 job」变为「一个 batch 下多个 job」，`GET /api/batches/{id}` 一次取回整批
- 并发：**全局单并发**——`threading.Lock` 以资源为粒度加锁，同一时刻只有一个资源在动网盘与台账，第二个批次排队（页面显示「排队中」）。不并行不是保守，而是三个硬约束：驱动内部单线程顺序传（百度分片、夸克 OSS 逐 part，无并发通道）；台账是无 WAL 的单文件 SQLite，多连接并发写会 `database is locked`（默认等锁 5 秒后直接报错）；网盘分享接口最容易被限频，批量时一次建 N 个分享，间隔越短越危险。串行还顺手消掉了「查同名 → 建目录」之间的竞态。官方没有公开具体 QPS 上限，因此不按猜测的数字做并行
- 理由：链接是交付物。一个资源一条链接、一个标题，才能「发出去的时候是一条条清楚的分享」；若把 3 部剧塞进一个文件夹，就没有独立的标题与链接可发。飞书同理：一节对应一个资源，才能按资源检索。批量若仍串行但不由系统排队，让人一个个点，等于把机械劳动留在人这边
- 原话：
  > 「如果想要批量上传，这里需要怎么改？或许上传的内容以及返回的链接这里的逻辑都要修一下」
  > 「注意并发或者可能存在的限制？我不知道有没有」
  > （选型确认）批量时多个对象在网盘上「各自一个文件夹」；飞书「每个资源一节」
- 落点：BACKEND §1 模块 / §2 REST 与批量契约 / §5 后台任务与并发；FRONTEND §2～§4；ARCHITECTURE §1 数据流；ISSUES（I-018 修订 A6–A10）

## D-008 · 2026-11-09 · 接入外部资源：发现 / 获取 / 加工 / 投放四层，能力用声明，默认同盘转存

- 原：系统只会「生产」——`publish_task` 的输入是本地路径，输出是我盘里的资源文件夹与链接。要接「别人盘里的资源」，直觉做法是给每个站点加一个驱动，但驱动契约的输入就是本地文件，把搜索、解析、风控塞进驱动会让「来源」与「目的地」两种身份混在一起（AC-03 也会被破：core 不得知道站点端点）
- 现：拆成四个可插拔层。`sources`（本地 / 分享链接 / 关键词搜索 / 后续订阅）只产出 `Candidate` 元数据，不含文件内容；`acquire` 由 core 按驱动**能力声明**（`capabilities` 含 `save_share` / `rename`）在「同盘服务端 save」与「跨盘下载再上传」之间选择；`transforms` 只做字符串级改名与结构拍平；`publish_task` 原样复用。加一个来源 = 加一个文件 + 注册一行，加一种加工同理
- 关键判断一：**搜索不是对接方式**。搜索站索引的是分享链接，它自己没有资源；能不能「对接」一个站点，取决于能否解析它的分享链接并转存进我的盘。所以搜索是可替换的「候选发现器」（现成可用 PanSou：MIT、13 种盘、`POST /api/search`、带判活接口），转存能力才属于网盘驱动
- 关键判断二：**同盘优先**。同盘转存是服务端操作（秒级、零流量、不破秒传）；跨盘没有服务端通道，必须下载再上传（一个 4GB 视频 ≈ 三倍时间与流量，且新 md5 会失去秒传、可能触发平台复审）。所以「我有很多盘」不等于「每个盘都要接转存」——搜到夸克就落夸克
- 关键判断三：**百度只当目的地**。百度开放平台无分享链转存接口，网页私有接口带强滑块/旋转验证码，无人值守必掉；115/123/天翼有网页实现可参考但需 Cookie 体系与实测。故能力矩阵是「能当目的地的盘多，能当源的盘少」
- 理由：站点会一直加，如果每加一个都要改编排层，这个系统长不到十个站点就会烂掉。四层 + 注册表 + 能力声明，才能做到「一条产线一段配置，一个新站点一个新文件」
- 原话：
  > 「我可能会对接很多网盘站点，也就是从他那里获得资源——转存——重命名或者把广告去掉或者增加我的广告——再分享」
  > 「这里能否做成一个模块化的东西？毕竟我可能有很多网盘站点，我想一个生产这样添加」
  > 「不过对接其他站点，应该是通过「搜索」的方式来对接的？这个你需要调研一下，或许也有其他方法」
- 落点：`SOURCES.md` §1–§7；ARCHITECTURE §1 数据流 / §2 模块表 / §3 AC-09～AC-11；BACKEND §1 模块 / §2 阶段 3 契约；PRD F6～F8；ISSUES（I-020 / I-021 / I-022 / I-023）

## D-009 · 2026-11-09 · 热度以「供给侧采样」为主，需求侧只做代理，样本不足就说不知道

- 原：没有热度概念。要做的话，最直觉的是「统计自己分享的转存数」，但网盘侧没有稳定接口给你这个数（夸克只有「我的分享」列表，百度没有），于是这条路在冷启动阶段没有数据
- 现：三层信号分开，各管各的问题——**供给侧**（定时跑搜索，记某关键词的链接增量、去重后的来源广度、存活率；不需要任何自有流量，第一天就有数据）、**需求侧**（自建分发落地页，记曝光 / 点击 / 复制；要等落地页做完）、**外部趋势**（豆瓣 / 微博 / TMDB / 热搜榜，只当先验权重，不进主分）。合成用 z-score + 分位数，展示排名与置信度；样本 < 30 显示「样本不足」
- 关键判断一：**先做供给侧**。它零流量冷启动，且直接回答「有多少人在传这个资源」；需求侧回答的是「有多少人在找我」，两者不是同一个问题，不能混成一个分
- 关键判断二：**去噪比加权重要**。同一资源被 50 个频道转发，说明有人批量分发，不等于很多人在找；所以计数前必须按 URL 去重，并把「来源广度」单独做一维。实测死链率可到 46%，热但全是死链就是假热，所以存活率也要进分
- 关键判断三：**不展示伪精确分数**。三个信号量级差几个数量级且随时间漂移，输出「87.3 分」是在骗自己；只给排名、趋势箭头、样本量与置信度
- 关键判断四：**信号要能被证伪**。滚动回测（T-7 的榜 vs T 日实际新增），相关性 < 0.3 的信号权重归零，而不是留着让榜更好看
- 原话：
  > 「另外一个需求是，我想知道当前什么资源比较热门，这里或许需要做一个热度检测工具，你有什么思绪吗」
- 落点：`SOURCES.md` §8；ARCHITECTURE AC-12；BACKEND 热度表与 REST 草案；PRD F9；ISSUES（I-024）

## D-010 · 2026-11-09 · 内容站并入本仓库（subtree，保留历史），内容收敛到一份 JSON，发布仍归站点仓库

- 关键判断四：**写内容可以自动，发布必须人按**。写 JSON 是本地的、可回退的；`git push` 到站点仓库等于对外公开。界面上线时只提示「已写入本地，需你确认后推送」

## D-015 · 2026-11-09 · 删除只做「远端递归删」，不给退路也不做回收站

- 原：驱动契约没有删除能力，每轮验收在网盘留下的 `/panup验收-*` 只能人工登网页删；台账里已失效的分享链接也一直留着
- 现：`Driver.delete(remote_paths, *, to_trash=True)` 统一契约（基类默认报 `PUP-422`，百度/夸克实现，**签名与 I-027 文件页的批量删除一致**），两个接口（单条记录 / 显式路径）加记录页「删远端」按钮；台账新增 `deleted` 状态，链接与提取码清空、行保留
- 关键判断一：**删除不放进基类抽象方法，但签名必须和 I-027 对齐**。百度/夸克之外还有未来的转存源驱动，强加抽象方法会让所有存量驱动与测试桩一起改；同时 I-027 的文件页已经写了同名 `delete`，两边各写一套签名合并时必然打架，所以本单直接采用它的批量契约（`deleted` / `missing` / `failed`），接口层只传一条
- 关键判断二：**幂等优先于严格**。远端本来就没有时进 `missing` 而不是 `failed`——删一批验收目录时最怕「删到一半重跑就红」，那样人只能一条条补
- 关键判断三：**只删远端，不删台账、不删本地副本**。台账行是「这个资源曾经发过」的唯一证据，删了就查不到它曾经存在；本地 `data/inbox` 副本另有清理入口
- 关键判断四：**不给「只删空目录」和「回收站」**。两个盘的删除都是服务端递归，没有空目录档；做回收站要么再建一套目录约定，要么依赖各盘自带的回收站（接口不一），都不如实明确「删了就没了」
- 边界：删除会让已分享的链接立刻失效（分享的是同一个 fid）；百度的写操作会偶发撞 `errno 132` 安全校验，等几秒重试即可（实测 16 个目录全删成功），接口把提示原样给出
- 原话：
  > 「1）增加删除接口，并把每一次的结果删除」
- 落点：`drivers/base.py`（默认 `delete`）、`drivers/baidu.py`、`drivers/quark.py`、`core/ledger.py`（`record_deleted` / `mark_deleted_by_remote` / `deleted` 聚合）、`web/api.py`（两个接口）、`web/static/app.js` + `styles.css`（按钮与徽标）、BACKEND §2、ISSUES / I-039
