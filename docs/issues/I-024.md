## 目标

- 意图：知道「现在什么资源热」，用来决定下一步拿什么、发什么（目标）；现在没有任何数据，只能凭感觉（现状）
- 行为：一张榜——关键词 / 趋势箭头 / 近 7 天曲线 / 各盘能搜到多少条 / 样本量与置信度；点进去能直接拿候选
- 机制：定时对一组关键词跑采样（复用 I-021 的搜索适配器），落 `heat_sample`；按天算 `velocity / breadth / alive_rate` → z-score → 分位数 → `heat_score`；榜只读表，不在请求里现算

| A1 | 机制 | 采样落库幂等：同一关键词同一天重复跑不产生重复行（唯一索引 `(kw, sampled_at)`） | 模型 | `test_sample_idempotent` |

## 边界

- **只做供给侧**。需求侧（曝光/点击/复制）要自建对外分发页，与「只监听 127.0.0.1」红线冲突，单独立项
- 不爬全网：只对配置里的一批关键词做定点采样，不是「全网热度」
- 不做机器学习排序；规则可解释、可回测、可关掉
- 外部热搜榜只作先验权重（≤10%），不作为主信号

## 风险与对策

- **样本偏差**：搜到多少条取决于 PanSou 的频道与插件配置，换个配置数字全变 → 榜上必须标「数据源」，跨配置的数字不可比
- **假热**：同一资源被批量转发 → 按 URL 去重 + 来源广度 + 存活率三重约束
- **信号漂移**：平台生态变化会让阈值失效 → 权重与阈值进配置，回测不过就归零，不硬调
- **过度承诺**：热度是代理，不是真值 → 界面上写清口径，不出现「全网最热」这种话

## 过程记录

- 调研结论（`SOURCES.md` §8）：网盘侧没有稳定的「我的分享被访问/转存」接口，所以需求侧数据只能自建落地页；供给侧的链接增量是零流量冷启动唯一可用的信号
- 一个反直觉的点：热度榜的价值不在「算出分」，而在「给出可回测的排名 + 能一键拿候选」；只算分不落地到动作，就只是个好看的表
