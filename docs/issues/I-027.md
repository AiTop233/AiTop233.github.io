## 目标

- 意图：盘里的资源传上去之后，改名、删掉、整理都得回网盘网页端一条条点。不做则「传完就管不了」，重复资源与脏名字只能累积（代价）
- 行为：管理台多一个「文件」页——选盘、进目录、勾选条目，批量改名（前缀 / 后缀 / 查找替换，带改前改后预览）与批量删除（弹窗列出要删的条目，移入回收站）
- 机制：驱动声明 `capabilities` 并实现 `rename` / `delete`（服务端一次调用）；`core/manage.py` 负责路径校验与**逐条成败**；REST 三个端点；前端一页 + 一个原生 `<dialog>`

## 与 I-022 的关系

「加自己的广告」在原始需求里指的是**名字层面**：给资源名带上自己的标识、或在资源文件夹里多放一个固定文件夹 / 说明文件。两者都不需要下载、转码、重传，因此分两层落地：

- **投放时**（I-022 的一部分，已随 `e578bfc` 落地）：`transforms/` 的 `clean`（删广告词）、`name`（模板 / 前后缀，幂等）、`notice`（追加固定目录或说明文件，分享前落地）
- **投放后**（本单）：盘里已有的资源批量改名 / 删除，走服务端接口

媒体级处理（去片头、贴片水印）仍是 I-023 的评估范围，**不在本单**。

接口实现依据：夸克 `POST /file/rename {fid, file_name}`、`POST /file/delete {action_type:1, filelist:[fid]}`（对照 alist 的 `quark_uc` 驱动）；百度 `POST /api/filemanager?opera=rename|delete`，`filelist` 为 JSON 字符串（照官方《管理文件》文档）。百度 `rename` 的 `newname` 先用全路径，遇 `-7` 自动退回纯文件名重试。

## 边界

- **不做复制 / 移动 / 转存 / 链接检测**：同一套壳子（选中 → 操作 → 逐条结果）可以直接加，但各自要补驱动的 `copy` / `move` / `save_share` 与链接解析，分成后续单
- **不做彻底删除**：两个盘都只做「移入回收站」，不可逆操作留给网盘网页端
- **不碰台账**：盘上改名 / 删除不改写 `uploads` 表——台账记的是「当时传到哪」，不是实时状态；对不上时以盘为准
- **不做拖拽移动、重命名冲突的自动改名**：同名冲突直接报错，由人决定改成什么
- **列表不分页**：一次列完当前目录（夸克驱动本身已自动翻页）；超大目录的虚拟滚动留待有实际需求时做
