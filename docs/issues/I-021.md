## 目标

- 意图：一条链接一条链接地粘太慢。要「搜一个词，把想要的几条一次性拿下来」，且能配成产线定时跑（目标）；现在只能人工在搜索站里翻，翻到再复制粘贴（现状）
- 行为：输入关键词 → 候选池（标题 / 盘型 / 大小 / 时间 / 来源数 / 是否存活）→ 勾选入队，或由产线按规则自动挑（每轮上限默认 3）→ 逐条转存分发
- 机制：`sources/pansou.py` 调 `POST /api/search` 并归一成 `Candidate`；入池前调 `/api/check/links` 判活；按 URL 去重、按标题聚合算「来源广度」；`run_line()` 读 `[[line]]` 配置执行 select → acquire → publish

## 边界

- 不自建爬虫：搜索能力全部来自外部服务（PanSou 或等价物），本项目只做适配与筛选
- 不做「全自动无限跑」：每轮有上限、有停机条件，调度最小粒度到「一次一轮」
- 不做语义搜索与打分排序的自研算法；排序用「新鲜度 + 来源广度 + 是否存活」三条可解释规则

## 风险与对策

- **死链率高**（实测样本 54% 存活）：入池前判活，死链不重试、不进主流程
- **同质刷屏**：计数前按 URL 去重，来源广度单独一维（否则「50 个频道转发同一资源」会被算成 50 条热度）
- **PanSou 依赖**：自建要 Docker + 代理访问 TG；外接则受对方可用性影响。两种都支持，配置里只写 `backend = "pansou"` + `base_url`
- **风控**：转存仍走 I-020 的串行 + 间隔 + 上限

## 过程记录

- 调研：PanSou（MIT，Go）`POST /api/search` 支持 `kw / cloud_types / plugins / channels / res=merge`，响应 `merged_by_type`；`POST /api/check/links` 批量判活；插件目录 `plugin/<name>/` + `ENABLED_PLUGINS`——「加一个站点」这件事可以下沉给它
- 结论：**搜索是可替换的发现器，不是对接方式**（D-008）。所以这一单只写一个 `sources/pansou.py`，将来换后端不动编排
