## 目标

- 意图：上传过程要**看得见**——现在传到哪个盘、第几个文件、飞书文档写了没（目标）；现在点「上传」后按钮一直转圈，几 GB 的文件夹要等几分钟，人分不清是在传、卡住了、还是已经在写飞书（现状）；不做则每次上传只能干等，出问题也不知道断在哪一步（代价）
- 行为：
  - 点上传后立刻出现进度卡片：先显示「把文件交给本地服务」的字节进度，随后每个网盘一行进度条（第 i/n 个文件、已传百分比），飞书一行（等待写入 / 写入中 / 已写入 / 未写入），下面一条「最新在上」的进展时间线
  - 远端目录**按配置回填、不留空**，并在输入框下方写出**实际落点**（含年/月/日与标题层），改标题、切「按日期建子目录」时实时更新
- 机制：
  - `POST /api/upload` 默认把任务交给后台线程并返回 `202 {job_id, ...}`；管道新增 `progress(event)` 结构化回调，把「扫描 / 查重 / 建目录 / 逐文件上传（字节）/ 分享 / 写文档 / 完成或失败」写进内存任务板 `web/jobs.py`；前端 `GET /api/jobs/{id}` 每 0.5 秒轮询渲染
  - `sync=1` 保留同步返回（测试、curl 与既有调用方）；`GET /api/options` 返回各盘默认目录供表单回填
  - 进度是**旁路**：回调抛错、前端断开都不影响上传本身；任务板只在内存，最终事实仍以台账为准

## 界面结构骨架

上传页在「表单」与「结果卡片」之间插一张**进度卡片**（详见 `docs/assets/I-019-progress.png`）：

- 标题行：左「任务标题」，右阶段句（`准备中…` / `上传到网盘 · 已完成 1/2 个网盘` / `网盘已传完，正在写入飞书…` / `已完成 · 2/2 个网盘 · 飞书已写入`）
- 进度行（每盘一条）：盘名 · 进度条 · 状态文字（`第 2/3 个 · 63%` / `完成` / `失败` / `已有记录`）· 当前文件名
- 飞书一行：盘名位写「飞书」，进度条只在写完后满格，文字给 `等待写入 / 写入中 / 已写入 / 写入失败 · 原因`
- 时间线：等宽时间 + 盘名 + 一句话，**最新在上**，最多回看 40 条

上传表单的网盘行改为「勾选 + 目录输入框 + 实际落点小字」两行结构（详见 `docs/assets/I-019-upload-defaults.png`）。

## 过程记录

- 管道侧只加旁路：`progress` 与既有 `on_progress`（驱动级字节回调，CLI 进度条在用）并存，`_emitter()` 吞掉回调异常——进度永远不许反噬上传
- 任务板 `web/jobs.py` 用 `threading.Lock` + 快照深拷贝：后台线程写、HTTP 线程读，前端每 0.5 秒只看快照
- 前端上传改 `XMLHttpRequest`（`fetch` 拿不到上传字节进度），本地这一段也照实显示；服务端 `202` 后转轮询
- 首版时间线是「最新在下 + 自动滚到底」，截图发现顶部被裁出半行（像排版坏了），改为**最新在上、不自动滚**；阶段句从「1/2 个盘已结束」改为「已完成 1/2 个网盘」（「已结束」会被读成失败）
- `finishUpload` 与轮询各调一次 `refreshRecords()`，收成一处
