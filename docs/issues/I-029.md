## 目标（草案）

- 意图：想知道自己分享的资源实际被访问、转存或下载的情况；目前没有经验证的统一报表，只能逐盘查看，难以判断哪些资源值得继续分发。
- 行为：先确认各盘实际提供哪些指标，再决定是否展示累计值、按日快照与可计算的区间增量；展示入口与首期范围待批准。
- 机制：建议由 drivers 解析平台响应，core 统一口径与快照，入口展示结果；接口、数据结构及依赖须在验证后另行确认，不以遗留草稿定案。

## 验证前置

本轮只登记验证任务，不发送真实请求。后续须使用本人账号取得可核对的观测记录：请求条件、脱敏字段、对应网页数值、账号权限、采集时间、分页覆盖及失败表现。记录不得包含 cookie、提取码或个人分享明细。

遗留代码声称百度 `/share/record` 提供 `vCnt` / `tCnt` / `dCnt`，夸克 `/share/mypage/detail` 提供 `save_pv` / `download_pv` / `visit_user_count`；这些只是待核实线索。现有文档没有足以复核的实测记录，不能据此承诺两个盘都可读，也不能把夸克 `click_pv=-1` 等取值推定为所有账号的固定行为。

## 范围建议与待确认

- 优先验证平台数据；每日快照、手动刷新或定时采集、CLI 与管理台各做到哪，验证后再定。当前不增设定时任务或启动服务。
- I-024 回答「什么资源在变热」，本单回答「自己的分享表现如何」。落地页点击 / 复制可另记，但不能等同于实际转存 / 下载，也不能填补平台数据的空缺。
- 链接状态可作为后续关联信息；主动判活及站点失效标记归 I-034，不能用一次列表缺失直接判定分享已失效。
- 分享维度与资源维度的映射、同一资源多次分享及多盘聚合、快照保留周期和迁移方案尚未确认。涉及新需求与数据结构，转待办前需在规划模式下补齐 PRD / ARCHITECTURE / BACKEND，并冻结标准。
