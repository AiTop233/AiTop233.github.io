## 目标

- 意图：把整个资源文件夹拖进浏览器就能传，网盘上结构与本地一致；一次能传多个资源（目标）；原实现拖文件夹**静默无反应**（`<input type="file">` 没开目录模式、drop 只取 `files[0]`），且「一次提交 = 一个资源」写死在接口与进度板里，多选与批量都进不来（现状）；不做则「资源包」只能先在资源管理器里拆开一个个传，传多部剧还要重复点几十次上传（代价）
- 行为：拖入文件夹递归读取并保留相对路径；可多选文件、也可一次拖多个文件夹；**每个顶层文件夹 = 一个资源**（自己的文件夹、自己的链接、飞书自己一节），无目录的一批文件合成一个资源；批量时标题框禁用（各资源用各自名字）；进度面板给出资源清单与当前资源的分盘细节；结果按资源分组并可「复制全部链接」；记录页每个资源一条，可单独重传
- 机制：前端 drop 用 `webkitGetAsEntry()` 递归（`<input webkitdirectory>` 兜底）；`POST /api/upload` 收 `files`（多值）+ `paths`（相对路径，一一对应）+ `pans` + `title` + `date_dir` + `doc`，落 `data/inbox/<批次>/<相对路径>` 还原目录树，按顶层目录分组后**逐资源串行**调 `publish_task`；返回 `202 {batch_id, count, resources}`；新增 `GET /api/batches/{id}` 一次取回整批；**全局单并发**（一次只跑一个资源），第二个批次排队

## 界面结构骨架

沿用 I-008 骨架（上传页），三处结构变化：

- 拖拽区：主文案「把文件或文件夹拖到这里」；选中后显示「2 个资源 · 4 个文件 / 2.6 GB · 点这里重选」
- 拖拽区下方：`[选择文件夹] [清空已选]` + 一行说明；再下方是已选资源小标签（名字 + 文件数 + 大小）
- 进度卡片：标题「批量上传 · N 个资源」，阶段行「x/N 个资源已结束 · 正在跑「…」」；资源行（名字 | 进度条 | 状态）下面是「当前」资源的分盘明细与时间线
- 结果卡片：按资源分组，每组「资源名 + 文件夹 · N 个文件 + 飞书写入状态」，组内是各盘链接；右上角「复制全部链接」

## 过程记录

- 接口从单 `file` 改成 `files` + `paths`；新增 `web/inbox.py` 负责「落盘还原目录树」与「按顶层目录分资源」，与网盘无关，可单测
- `jobs.py` 加 batch：一次提交 = 一个 batch + 每资源一个 job，`GET /api/batches/{id}` 聚合；淘汰时按最大批大小抬高保留量，避免一批里靠前的资源被挤掉
- 并发：全局 `threading.Lock`，资源粒度加锁。不是性能取舍而是约束——驱动单线程顺序传、台账是无 WAL 的单文件 SQLite、分享接口易限频；串行同时消掉同名文件夹竞态
- 前端：`state.picked`（file + 相对路径）取代单个 `state.file`；拖放走 `webkitGetAsEntry()` 递归（`readEntries` 每次最多 100 条，读到空为止）；`<input webkitdirectory>` 兜底
- 上传端点从 `async def` 改回 `def`：`ingest` 是磁盘 IO，放线程池才不会堵住进度轮询
