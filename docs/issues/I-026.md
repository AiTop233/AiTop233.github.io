## 目标

- 意图：上传完一个资源，分享链接已经在台账里，但内容站上还是空的——要发出去就得手工去 `data/resources.json` 里再写一遍。不做则「上传」和「分发」是两条手工流水线，站上的内容会长期落后于盘里的内容（代价）
- 行为：一次上传（或对一批已上传记录）→ 站点 `data/resources.json` 多出对应条目（标题 / 链接 / 提取码 / 大小）→ 本地构建可见；推送发布由人决定
- 机制：core 提供「把任务导出成站点条目」的纯函数（可测、不碰网络），CLI / Web 各接一个入口，写盘统一走 `site/tools/add.mjs`（唯一写入点，见 I-025）

## 边界

- **不自动发布**：写本地 JSON 可以自动，`git commit/push` 必须人按。发布是对外行为，不该由上传流程代劳
- **不改 `publish_task` 的返回结构**：同步是旁路，失败只记日志与 job 事件，不回滚上传
- **不做编辑与下架**：站点条目的改名、删除另开单（大概率要配合「链接判活」）
- **不做 SEO 批量生成**：不按标题批量造落地页

## 风险与对策

- **内容合规**：站点是对外公开的，同步等于公开分享。对策：默认关闭，开启时在 UI 上写明「会出现在公开站点」
- **链接失效**：站点卡片长期挂着可能变死链。对策：后续由 I-034 评估已发布链接检测，可研究复用 I-021 的候选判活；失效标记不在本单，不归入 I-024 热度统计
- **重复内容伤 SEO**：多盘同一资源若各建一页会稀释权重。对策：一个资源一张卡片（多链接），不按盘分页
- **数据膨胀**：单文件规模扩大可能影响构建与 diff。现阶段保持 AC-13 的唯一内容源；确有性能问题时先观测，拆分数据源须另提规划变更，不按条数自行改结构
