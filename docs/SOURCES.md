# 资源渠道：发现 → 获取 → 加工 → 投放

> 阶段 3 的设计文档。回答两件事：**别人盘里的资源怎么接进来**（可插拔、一条条加），**什么资源值得接**（热度）。
> 不写实现细节（→ BACKEND / 代码）；不写先后顺序（→ 看板）。

## 0. 一句话

现有系统只会「生产」：本地文件 → 我的盘 → 链接。要支持「别人的资源 → 我的盘 → 我的链接」，不能给每个站点加 `if`，而要把**资源从哪来**拆成三个可插拔的插件点：**发现（Source）/ 获取（Acquire）/ 加工（Transform）**，投放（Publish）复用现有驱动与管道。

## 1. 为什么不是「给每个站点加一个驱动」

直觉做法：既然有 `drivers/`，那再加几个站点驱动就行了。但驱动契约是 `mkdir / upload / share / list`——**输入是本地文件**。别人盘里的资源不是本地文件，它是一串「分享链接 + 提取码」。给 `upload` 加分支会同时踩三个坑：

1. 驱动层被迫懂「搜索」「解析」「风控」，与 AC-03「上游响应解析留在驱动内部、core 只消费契约」冲突；
2. 「搜到的资源在夸克、要放到百度」这种跨盘需求，在驱动层无法表达——它是编排问题，不是适配问题；
3. 站点增多后，`drivers/` 会变成「既是目的地又是来源」的双重身份，能力边界消失。

所以分层，且**插拔点是两个而不是一个**：搜索站只提供「候选」，转存能力属于网盘驱动。

## 2. 四层与契约

```
Source.discover(query)      → [Candidate]      发现：本地路径 / 关键词 / 分享链接 / 订阅
        ↓  select（筛选排序，人挑或规则挑）
Acquire(candidate, pan)     → 我的盘里的路径   获取：同盘 save（秒级）或 跨盘 relay（分钟级）
        ↓
Transform.apply(resource)   → resource         加工：名字（零成本）/ 媒体（重成本）
        ↓
Publish(resource, targets)  → 各盘文件夹链接   投放：现有 publish_task（mkdir/上传/改名/分享）
        ↓
Writers.append_task         → 文档一节         记录：现有飞书写入端
```

四层各自的数据形状（草案，字段名以 BACKEND 为准）：

| 层 | 输入 | 输出 | 现有代码 |
|---|---|---|---|
| Source | `query`（路径 / 关键词 / 链接 / 规则） | `Candidate{source, ref, title, pan, pwd, size, file_count, created_at, score, extra}` | 新增 `src/panup/sources/` |
| Acquire | `Candidate` + 目标盘 | `{path, pan, size, files, cost}` | `drivers/*.save_share()` + core 编排 |
| Transform | 资源（名字 + 文件清单 + 可选本地路径） | 同形状，改过的字段 | 新增 `src/panup/transforms/` |
| Publish | 资源 + `targets` | 现有 `{items, failed, writers}` | `core/pipeline.publish_task` |

关键约束：**`Candidate` 里没有「文件内容」**，只有「怎么拿到它」。所以发现层可以只跑几百毫秒、只产出元数据；要不要真的拿，是下一步的事。这让「搜 50 条、只挑 3 条」变得便宜。

## 3. 发现层：搜索不是「对接方式」

> 人问：对接其他站点，应该是通过「搜索」的方式来对接？

不是。搜索站索引的是**分享链接**，它自己没有资源。真正的「对接一个站点」由两件事组成：**能解析它的分享链接** + **能把文件转存进我的盘**。搜索只是「候选发现器」，换一个搜索源不改变对接能力，换一个网盘的转存实现才改变。

据此，发现层有三类实现，都可插拔：

| 类型 | 输入 | 实现 | 依赖 | 成本 |
|---|---|---|---|---|
| `local` | 本地路径 | 现有上传（`_scan_source`） | 无 | 已有 |
| `link` | 一条分享链接 + 提取码 | 解析链接 → 解出 `pan + share_id + pwd` → 直接成为 `Candidate` | 各盘链接格式 | 极小 |
| `search` | 关键词 | 调外部搜索服务，取回候选池 | 见下 | 中 |
| `feed`（后续） | RSS / TG / 公众号 | 订阅源解析成候选 | 源格式 | 中 |

### 3.1 搜索这一层怎么接（调研结论）

现成可用的东西是 **PanSou**（Go，MIT）：聚合 100+ Telegram 频道 + 80+ 站点插件，输出结构化 JSON，支持 13 种网盘类型，自带链接有效性检测。

- 接口：`POST /api/search`，请求 `{kw, cloud_types, plugins, channels, res:"merge", refresh}`；响应 `{total, results, merged_by_type}`，每条链接是 `{type, url, password, datetime}`，`source` 形如 `tg:频道名` / `plugin:插件名`。
- 另有 `POST /api/check/links`：批量判活，状态 `ok / bad / locked / unsupported / uncertain`。
- 部署：`docker run -p 8888:8888 ghcr.io/fish2018/pansou`，或源码构建（Go 1.18+，访问 TG 需代理）。
- **它本身也是插件化的**：`plugin/<名字>/` 一个目录一个源，`ENABLED_PLUGINS` 显式启用。这正好对上「我可能有很多站点，想一个一个加」——加站点这件事可以交给 PanSou，我们只做一层 `sources/pansou.py` 适配。

因此 `sources/` 只做薄适配：`discover(kw)` → 调 PanSou → 归一成 `Candidate`。换搜索后端（自建 PanSou / 别人的实例 / 某站点私有接口）只换一个文件。

**必须承认的两个数据质量问题**（实测报告，非猜测）：

1. **死链率高**：某次抽样 141 条去重链接只有 76 条存活（54%）。所以候选进池必须判活，且死链要打标、不重试。
2. **同质刷屏**：同一资源被几十个频道重复发。所以排序不能只看条数，要看**去重后的源广度**（见 §6）。

### 3.2 三类发现的分工

- 临时找一个资源 → 粘贴链接（`link`），最快，无依赖。
- 找一批同类资源 → 关键词搜索（`search`），候选池 + 人挑。
- 长期跟一个题材 → 订阅（`feed`）+ 产线定时跑，看到新的就转。

## 4. 获取层：同盘秒级，跨盘分钟级

这是整个设计里最影响成本的一条。转存有两种物理路径：

| 路径 | 条件 | 动作 | 耗时 | 流量 | 是否破坏秒传 |
|---|---|---|---|---|---|
| `remote_copy` | 源盘 == 目标盘，且该盘支持 `save_share` | `resolve_share → save_share(dest) → rename`，全程服务端 | 秒级 | 0 | 不破坏 |
| `relay` | 源盘 != 目标盘，或目标盘不支持转存 | 下载到 `data/relay/` →（可选加工）→ 上传 → 删临时 | 分钟～小时 | 下行 + 上行 | 破坏（新文件新 md5） |

结论（D-008）：**默认同盘转存再分享**。搜到夸克资源就落夸克、发夸克链接；要发到百度，那是另一条产线的事，且明确标为「重成本」。这消掉了「必须给每个盘都实现转存」的伪需求。

### 4.1 能力矩阵（不是所有盘都能当源）

驱动增加**能力声明**，编排层据此判断可行性，而不是 `try/except` 猜：

```python
class Driver:
    capabilities = frozenset({"mkdir", "upload", "share", "list"})
    # 转存源再加 "save_share"；能服务端改名再加 "rename"
    def supports(self, cap: str) -> bool: return cap in self.capabilities
```

现状与调研（**标「待实测」的表示只有公开实现/他人实测，本项目未自测**）：

| 盘 | 上传/分享 | 分享链转存 | 服务端改名 | 备注 |
|---|---|---|---|---|
| 夸克 | ✅ 已有 | ✅ 待实测（协议已明确） | ✅ | `sharepage/token → detail → save → task` 四步 |
| UC | — | ✅ 协议与夸克同构（同一套 `clouddrive`，换 base 与 UA） | ✅ | 接 UC 的成本远低于其它新盘 |
| 百度 | ✅ 已有 | ⚠️ 仅网页私有接口，强滑块/旋转验证码 | ✅ | 无人值守不稳定，**只当目的地** |
| 115 / 123 / 天翼 | — | ⚠️ 有网页实现可参考，待实测 | 待实测 | 各自 Cookie 体系 |
| 迅雷 / 移动云盘 | — | ❌ 公开实现里没有稳定的转存 | — | 不接（成本高、留存风险） |

这张表就是「我有很多站点」的过滤器：**能当源的盘其实很少**，而能当目的地的盘可以很多。所以扩张顺序是「先加目的地（上传/分享），再按需加源（转存）」。

## 5. 加工层：先做零成本的，别急着上 ffmpeg

加工分两类，成本差一个数量级，必须分开排期：

| 类型 | 例子 | 在哪做 | 成本 | 风险 |
|---|---|---|---|---|
| `name` 名字 | 统一命名模板、去广告词、加前缀、`第01集` → `S01E01` | 上传前改本地名 / 转存后服务端改名 | 0，毫秒 | 同名冲突、改名后与原资源对不上 |
| `structure` 结构 | 拍平多余层级、按季/集归位 | 同上 | 0 | 结构判断错会毁掉资源 |
| `media` 媒体 | 去片头广告、贴片水印、转码 | **必须落地**：下载 → ffmpeg → 重传 | 一个 4GB 视频 ≈ 3 倍时间与流量 | 破坏秒传；md5 变了可能触发平台复审；画质损失 |

结论：`name` 与 `structure` 是纯字符串变换，做成 `Transform` 插件、按序执行、可组合；`media` 单独立项，先只做「能跑通一个文件」的验证，不进主链路。

命名模板用占位符，别做成固定规则：`{title}`、`{season}`、`{episode}`、`{quality}`、`{ext}`，加 `strip`（要清掉的词）与 `prefix`/`suffix`。例：

```toml
[line.transform.name]
template = "{title} S{season:02}E{episode:02} [{quality}]"
strip = ["广告", "加群", "更多资源", "www\\.[a-z0-9.]+"]
```

## 6. 产线（Line）：一条 TOML = 一条生产线

人说的「我想一个生产这样添加」，落到配置就是一段 `[[line]]`，不改代码：

```toml
[[line]]
name = "短剧 · 夸克转存分发"
enabled = true
schedule = "0 9,21 * * *"          # 一天两次；不填 = 只手动触发

[line.source]
type = "search"
backend = "pansou"
keywords = ["十八线资源", "短剧"]
cloud_types = ["quark"]
check_links = true                 # 进池前判活，死链丢弃

[line.select]
min_files = 2
max_age_days = 7
dedupe_by = "title"
limit = 3                          # 一轮最多拿 3 个，控制风控
order = "freshness"

[line.transform.name]
template = "{title}"
strip = ["广告", "加群"]

[[line.target]]
pan = "quark"
dir = "/003-十八线资源"
doc = "feishu"
```

字段含义与失败语义：

- `select`：先过滤再排序再截断，**`limit` 是风控阀门**，不是可选项；默认 3。
- `dedupe_by`：默认按标题去重（跨源同资源只留最新的一条），可改 `title+size`。
- 同一轮里多个候选**串行**处理（沿用 D-007 的全局单并发）；一条失败不影响下一条。
- 同名资源文件夹已存在 → 跳过并记「已存在」，不报错（批量场景里报错会淹掉真问题）。

## 7. 失败、风控与红线

- **风控**：转存与分享是平台最敏感的两个动作。串行 + 每步间隔 + 单轮上限；连续失败 3 次停掉该产线并亮红灯，不自动无限重试。
- **死链**：判活为 `bad` 直接丢；`uncertain` 进「待定」不进主流程。
- **内容留存**：有的盘会在转存后若干小时静默删除受审内容。产线必须能「事后巡检」——分享出去 N 小时后回查文件是否还在，不在就标记，而不是让人以为还在。
- **红线**：只处理公开分享；不破解、不绕过提取码、不碰付费内容；广告注入默认关闭（二次分发的责任与平台规则自担）；不把「转存」做成对平台的批量抓取。

## 8. 热度检测

### 8.1 先定义「热」是什么

「热」至少要能回答三个不同的问题，混在一起算就会得出没用的分数：

| 问题 | 信号 | 数据从哪来 | 冷启动 | 可信度 |
|---|---|---|---|---|
| 有多少人在**传**它 | 供给侧 | 定时跑 PanSou，记录关键词的链接增量 | 立刻可用 | 中（受索引覆盖影响） |
| 有多少人在**找/拿**它 | 需求侧 | 自己分发页的曝光/点击/复制 | 需先有分发页 | 高（但样本小） |
| 平台说它**火** | 外部趋势 | 豆瓣/微博/TMDB/热搜榜 | 立刻 | 低，只做先验 |

关键判断（D-009）：**先做供给侧**。它不需要任何自有流量，第一天就有数据；需求侧要先有分发落地页，属于第二阶段；外部榜只用来给关键词一个先验权重，不参与主分。

### 8.2 供给侧怎么采

不需要爬全网，只需要一个**固定观察窗**：每天对一组关键词（榜单候选 + 自己关注的题材）跑一次 `POST /api/search`，把结果落成样本：

```
heat_sample(id, kw, sampled_at, total, new_links, unique_sources, alive_links, top_titles)
```

由样本算三个指标：

- `velocity = 近 24h 新增去重链接数 / 前 7 天日均` —— 增速，热的核心
- `breadth = 去重后不同 source 数` —— 防单频道刷屏造成的假热
- `alive_rate = 存活链接 / 去重链接` —— 热但全是死链 = 假热（实测死链率可到 46%）

一个必须做的去噪：**按 URL 去重后再计数**。同一资源被 50 个频道转发，说明的是「有人批量分发」，不等于「很多人在找」。

### 8.3 需求侧：平台指标待验证，落地页事件另计

网盘侧是否提供适用于本人账号的访问、转存与下载统计，尚缺可复核的验证记录；接口线索与验证前置见 I-029，不能先断言没有接口，也不能把遗留代码的实测声称当成已验证。若另行批准分发落地页，可增加自己的观测点：

- 分享时同时生成 `panup` 落地页 `http://127.0.0.1:8256/s/<slug>`（对外用内网穿透/短链），页面只有标题、简介、各盘按钮。
- 记三个事件：`view`（打开）、`intent`（点了某个盘）、`copy`（复制了链接/提取码）。
- 跳转目标带上 `?from=panup&slug=xxx`，如果哪天网盘侧能看来源，就能对上。
- 这套数据可观测分发效果；低点击率只是待排查线索，不能仅据此判定标题或封面有问题。

这里必须诚实：`copy` 不等于「真的转存了」。没有网盘侧接口时，它是**代理指标**，界面上要标「代理」，不能当成转存数展示。

### 8.4 合成与展示

```
raw = 0.5*z(velocity) + 0.2*z(breadth) + 0.2*z(alive_rate) + 0.1*prior
heat = 分位数(raw)            # 展示排名与分位，不展示原始分
confidence = min(1, 样本数 / 30)
```

- 用 **z-score + 分位数**而不是加权原始值：三个信号量级差几个数量级，且会随时间漂移。
- 样本不足（`confidence < 0.3`）时显示「样本不足」，不给排名——**宁可说不知道，也不要给一个看起来精确的假数**。
- 页面形态：一张榜（关键词 / 趋势箭头 / 近 7 天曲线 / 各盘可搜到的条数 / 样本量与置信度），点进去看候选池，能一键「拿这条」。

### 8.5 怎么证明这个分数有用

用回测，不用感觉：取 T-7 的榜单，看 T 日实际新增链接是否真的高于均值（Spearman 相关）。若某信号相关性 < 0.3，把它的权重归零——**信号无效就砍掉，而不是留着让榜看起来更丰富**。

## 9. 分阶段与不做

| 阶段 | 做什么 | 为什么这个顺序 |
|---|---|---|
| S1 | `Source` / `Transform` 骨架 + `link` 源 + 夸克 `save_share` | 一条链接手动转存是最小闭环，能验证协议与风控 |
| S2 | `pansou` 源 + 候选池页 + 产线配置 + `name` 加工 | 这是人真正要的「批量拿资源」 |
| S3 | 热度：供给侧采样 + 榜单 | 有候选池之后，榜才有落点 |
| S4 | 分发落地页 + 需求侧信号 | 需要对外发布，独立评估 |
| 不做 | 媒体加工进主链路、迅雷/移动盘转存、无上限批量抓取 | 成本与风险不成比例 |

## 10. 未决

- PanSou 是自建（Docker + 代理）还是外接现成实例？自建可控但要多一个常驻服务。
- 转存目标盘先做哪个：夸克（协议已明确）还是 UC（同构、成本低）？
- 落地页要不要对外发布？发布就要处理「谁都能访问」的问题，与「只监听 127.0.0.1」的现有红线冲突。
- 广告注入做不做？技术上是 ffmpeg 叠图层，非技术上是二次分发的责任问题。
