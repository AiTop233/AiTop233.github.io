# 架构：网盘自动上传

> 阶段 1 为 CLI + 本地监控（无图形界面）；**阶段 2 起有前端**——本地 Web 管理台（浏览器访问，F4）：前端代码组织见 `FRONTEND.md`，界面结构与视觉约定见 `DESIGN_SYSTEM.md`。桌面端仍在「后续阶段」。

## 1. 数据流

```
本地资源（三种入口；一个资源 = 单个文件或一个文件夹）
  ├─ CLI 手动指定（F1；一次可指定多个网盘，各自目录）
  ├─ watcher 监控目录新文件（F2；阶段 2 起监控根的「网盘@远端目录」约定文件夹自动成为规则，F5）
  └─ Web 管理台拖入文件/文件夹（F4；一次可拖多个资源——每个顶层文件夹各成一个资源，网盘多选 + 每盘目录）
          │
          ▼
core 上传任务（publish_task）：一个资源 → 按网盘逐个跑单盘管道
  单盘管道：检查同名资源文件夹（已存在即报错，不合并）→ 建「基础目录/[日期/]标题/」并按相对路径建子目录
            → 逐文件上传（重传时跳过已存在且大小一致的文件）→ 分享**该文件夹** → 台账
          │                                   │
          │                                   ├─► 台账（SQLite）：每个「资源 × 网盘」一行，同任务共享 group_id
          │                                   ▼
          │                         任务聚合：资源 + 各盘文件夹链接 + 失败项
          │                                   │
          │                                   ├─► writer（飞书）：最顶插入**一节**（h2「YYMMDD 标题名」+ 成功盘各一行，链接指向文件夹）
          │                                   ├─► 内容站（可选）：追加一条资源到 site/data/resources.json，公开页按分类渲染（D-010）
          │                                   └─► 待修列表：失败项留台账，页面与 CLI 可重试
          ▼
输出：CLI 打印各盘链接 / watch 日志 / Web 页面展示链接与记录
```

一句话：本地的文件或文件夹（一个资源）经上传任务分发到一个或多个网盘，在每个盘上落为一个以标题命名的资源文件夹并生成指向它的分享链接，一个任务的链接合并写入飞书文档一节，全过程记入本地台账；一次提交可以带多个资源（各自一个文件夹、一条链接、飞书一节），资源之间串行排队；阶段 2 起浏览网页即完成上传、记录查看、待修重试与监控管理。

Web 入口另有一条**进度旁路**（D-006）：`POST /api/upload` 落盘分组后立刻返回批次号，上传任务在线程里按资源**串行**跑（全局单并发，D-007），管道把「扫描 / 各盘上传字节 / 分享 / 写文档」以结构化事件丢进内存任务板，页面轮询整批快照画进度。这条旁路不改变数据流主干——任务板只在内存，进程退出即丢，链接与成败仍以台账为准；进度回调抛错也不影响上传。

阶段 3 多一条**获取**链路（设计见 `SOURCES.md`），它与上传链路在「投放」处汇合：

```
远端资源（一条分享链接 / 关键词搜到的候选）
          │
          ▼
sources.discover(query) → [Candidate]（标题、盘型、链接、提取码、大小、新鲜度；**不含文件内容**）
          │   select：过滤 → 去重 → 排序 → 截断（limit 是风控阀门，默认 3）
          ▼
acquire（core 编排，按驱动能力选择路径）
   ├─ 同盘 + 驱动声明 save_share → 服务端 save → rename（秒级、零流量、不破坏秒传）
   └─ 跨盘 → 下载到 data/relay/ →（可选加工）→ 上传 → 清临时（分钟级、破坏秒传）
          ▼
transforms（名字模板 / 广告词清洗 / 结构拍平，纯字符串，不碰内容）
          ▼
publish_task（与本地来源同一条投放管道：同名检查 → 建文件夹 → 上传或改名 → 分享 → 台账 → 飞书）
```

一句话：**来源可以变，投放只有一条**。所有资源最终都收敛到「我的盘里一个以标题命名的文件夹 + 一条指向它的链接 + 台账一行 + 飞书一节」，这也是为什么获取层不需要重写投放逻辑。

现状与目标的差距：阶段 1 的 I-001 ～ I-006 代码已完成并全部验收；阶段 2 的 I-007 / I-015 / I-016 / I-017 / I-019 / I-018 代码已完成，待人验收（合并顺序见看板）；剩余差距是目录约定解析（F5）与监控页（I-009 / I-010）。阶段 3 只有设计（`SOURCES.md`），代码未动。

## 2. 模块分类与依赖方向

分类框架：**接入层**（网盘、文档写入）/ **核心**（管道、台账、配置）/ **入口**（CLI、watcher；未来的 Web、桌面、MCP）。

| 模块 | 在数据流中的职责 | 代码目录 | 允许依赖 | 禁止依赖 |
|---|---|---|---|---|
| drivers | 网盘客户端：登录态校验、建目录、上传、创建分享；**能力声明**（`capabilities`：上传 / 分享 / 转存 / 改名）决定它能否当来源 | `src/panup/drivers/` | config | core、writers、入口 |
| sources | 资源发现：本地路径 / 分享链接 / 关键词搜索 → `Candidate`（只有元数据，没有文件内容） | `src/panup/sources/` | config | core、drivers、writers、入口 |
| transforms | 资源加工：名字模板、广告词清洗、结构拍平（纯字符串变换，不改内容） | `src/panup/transforms/` | config | core、drivers、writers、入口 |
| writers | 文档写入端：向指定文档追加记录 | `src/panup/writers/` | config | core、drivers、入口 |
| core | 上传任务编排（一个资源分发到多个网盘）、**产线编排（发现 → 获取 → 加工 → 投放）**、资源文件夹化与单盘上传管道、同名检查、台账、驱动 / 写入端 / 来源 / 加工注册表 | `src/panup/core/` | drivers、writers、sources、transforms、config | 入口 |
| cli | 命令入口：upload / status / watch / serve 转发 | `src/panup/cli.py` | core | drivers、writers |
| watcher | 目录监控，产出新文件事件交给 core；阶段 2 支持约定目录动态规则 | `src/panup/watcher.py` | core | drivers、writers |
| web | 本地管理台服务端（FastAPI REST API + 托管 SPA 静态资源） | `src/panup/web/` | core、watcher | drivers、writers |
| config | 配置与密钥加载、启动校验 | `src/panup/config.py` | — | — |
| site | 内容站（VitePress）：把资源的「标题 + 分享链接 + 提取码」渲染成公开页面；内容源是 `data/resources.json`，唯一写入点 `tools/add.mjs`（D-010） | `site/` | — （独立 node 构建，不 import Python 代码） | 入口、core、drivers（只通过 JSON 文件与 CLI 交互） |

依赖方向：入口（cli / watcher / web）→ core → drivers / writers / sources / transforms → config，单向；drivers、writers、sources、transforms 四者之间互不依赖（sources 只认链接格式，不认驱动；transforms 只认字符串）。

通信契约按「未来会新增」设计：新增一个网盘 = `drivers/` 下新增一个驱动文件并在注册表登记一行；新增一个来源 = `sources/` 下新增一个文件并登记（只输出 `Candidate`，不碰网盘）；新增一种加工 = `transforms/` 下新增一个文件并登记；新增一个写入目标 = `writers/` 下新增一个文件并登记；新增一个入口（桌面 / MCP）= 调 core 公开函数或 REST API，不改 core；Web 前端只消费 REST API（`/api/*`），不 import 服务端内部。

技术栈：

- **Python 3.13 标准库优先**（已验证的零依赖实现可照搬）：`urllib` 解决 HTTP 调用，`sqlite3` 解决台账存储，`tomllib` 解决配置读取，`argparse` 解决 CLI，`logging` + 手写 JSON lines 解决日志。适用：个人本机工具、装机门槛低；不适用：当出现需要并发框架或异步 I/O 的需求时（后续阶段再评估）；风险：无第三方生态兜底，接口层改动需自己维护。
- **飞书开放平台 docx API 直调**：官方文档明确、个人自建应用可用。适用：向既有文档追加块；不适用：批量管理整个云空间时（权限模型不同）；风险：接口限频（个位数次/秒），串行调用即可。
- **Web 服务端 FastAPI + uvicorn（阶段 2，人选定）**：解决「管理台 REST API + 文件流式上传」。适用：本地单用户管理台、需要自动接口文档与校验时；不适用：当需要分发给他人部署时（会引入配置与安全面）；风险：引入两个第三方依赖（打破零依赖，AGENTS §11 条款 2 已随之修订），升级依赖时锁版本。前端为免构建 SPA 静态资源（原生 HTML/JS/CSS），由 FastAPI 托管，不引入 Node 构建链。被否决：标准库 http.server（multipart 流式解析与异步转发自造成本高于两个依赖）；Flask（无原生异步与校验，优势不再）。
- **目录监控用标准库轮询起步**（间隔可配，默认 5 秒）：零依赖；若轮询不满足再评估引入 `watchdog`（引入前须在 issue 里说明理由并更新本节）。
- 被否决的候选见第 4 节。

核心实体与关系：一次**上传任务**（一个本地资源——文件或文件夹 + 人给的标题 + 若干「网盘 × 目录」）在一个盘上落为一个**资源文件夹**，产生 N 条**上传记录**（本地资源、某网盘、**资源文件夹路径**、分享链接、提取码、状态），记录共享 `group_id` 指向同一任务；表结构与字段 → BACKEND。

## 3. 架构级红线（约束）

按主题分组，每条同行写「怎么检查」：

**模块边界**

- **AC-01** 入口（cli / watcher）不得直接 import drivers / writers，一律经 core ｜ 检查：评审核对 import 方向
- **AC-02** 新增网盘或写入目标只新增注册文件与注册表一行，不改既有模块 ｜ 检查：评审新增驱动的 diff，应只含新文件 + 注册表一行
- **AC-03** 网盘与文档接口的响应解析只发生在 drivers / writers 内部，core 只消费契约返回值 ｜ 检查：评审时确认 core 无网盘端点常量
- **AC-09** 来源层只产出 `Candidate`（元数据），不得自己下载或上传；走「同盘 save」还是「跨盘 relay」由 core 按驱动**能力声明**决定 ｜ 检查：`sources/` 内无 `drivers` import、无落盘代码
- **AC-10** 网盘能力用声明（`capabilities` / `supports()`），不得用 `try: ... except NotSupported` 或「先试再降级」来探测 ｜ 检查：评审转存路径代码，无能力探测式异常捕获

**安全边界**

- **AC-04** 凭据（网盘 cookie、飞书 app secret）只存 `secrets/` 或环境变量，不进仓库、不进日志 ｜ 检查：`git status` 不出现 secrets；日志文件中 grep 不到 cookie 值与提取码
- **AC-05** 日志与台账不得记录 cookie、secret 明文 ｜ 检查：评审日志字段清单 + 抽查日志文件

**失败可见**

- **AC-06** 驱动与写入端失败必须显式报错（含 errno / 错误码与恢复指引），不得用默认值、空返回或静默重试把失败伪装成成功 ｜ 检查：验收时人为使 cookie 失效，确认报错文案与退出码
- **AC-07** 监控上传必须去重：同一文件（路径 + 内容指纹）不重复上传，重启后依然 ｜ 检查：验收时放入同一文件两次并重启监控，台账只有一条成功记录

**风险边界**

- **AC-08** cookie 方案的操作保持低频串行（批量场景逐文件间隔 ≥ 1 秒），不做高频并发，降低风控风险 ｜ 检查：评审批量路径代码无并发上传调用
- **AC-11** 转存与分享一律串行，单轮候选有上限（默认 3），连续失败 3 次停线亮红灯，不自动无限重试 ｜ 检查：评审产线循环代码 + 人为断网跑一轮，确认真会停
- **AC-12** 热度榜不得把代理指标（点击/复制）写成「转存数」；样本不足必须显示「样本不足」，不得输出无置信度的精确分数 ｜ 检查：评审接口字段名与页面文案
- **AC-13** 内容站只消费 `site/data/resources.json`，分类页不得内联资源数组；任何写入走 `site/tools/add.mjs`（手工、脚本、同步共用一条路）｜ 检查：评审时确认分类页只有 `import ... data/resources.json`，无 `const resources = [...]` 字面量

项目私有规则：以上全部为本项目私有约束，不与其他项目共用。

## 4. 关键选择的理由

- **网盘接入走 cookie 网页版接口**：分享链接个人可创建，接口流程已在本地实测可用（2026-11，百度上传 + 分享全链路验证通过）。否决官方开放平台 OAuth（分享 / 上传接口需企业认证主体，个人申请不下来；且多一套 token 刷新与回调基建）。风险：cookie 会失效、有风控可能，恢复方式 = 重新登录导出 cookie；接口改版可能失效，靠错误显式暴露（AC-06）而非静默。
- **驱动抽象对齐 alist 的 Driver 设计（裁剪子集）**：alist 的网盘驱动接口成熟稳定，新增网盘照其流程移植，不重新发明接口语义。否决每个网盘自造一套方法名（扩展时接口漂移，上层要跟着改）。
- **核心与入口彻底分离**：CLI 与 watcher 是第一层薄壳；Web 端、桌面端、MCP server（后续阶段）共用同一 core，新增入口不改核心。否决把业务逻辑写进 CLI（未来每个入口都要重写一遍）。
- **台账用 SQLite 单文件**：去重（AC-07）与失败记录需要条件查询和唯一索引。否决 JSON 文件（并发写与按指纹查询都要自己造）。
- **标准库优先、零第三方依赖起步**：已验证的零依赖实现证明可行，装机门槛最低。否决起步就引入 requests / fastapi（阶段 1 没有任何一个 issue 需要它们；出现需求时按第 2 节的适用条件评估）。
- **飞书先行、腾讯文档列后续阶段**：飞书官方 docx API 个人自建应用即可用；腾讯文档开放平台的在线文档写入权限门槛高。否决先做腾讯文档（会阻塞 F3）。
- **轮询监控起步**：零依赖够用；否决起步即引入 watchdog（个人目录监控频率低，暂无 issue 需要）。

## 5. 可观测性总览

- 档位：本地小工具
- 日志去向与查询入口：JSON lines 落 `logs/` 按天滚动，一条 grep 命令查询（字段、事件目录、保留与脱敏 → BACKEND「日志、指标与告警」）
- 事件 / 错误码目录：由 BACKEND 定义（`core/errors.py` 常量表 + 文档；执行期建）

## 6. 交付与升级

- 分发形态：只在本人的机器上运行（自用工具）
- 制品怎么到用户手里：不适用——本机 git 仓库即制品；换机器时 clone + 按 BACKEND「配置与密钥」重新配置凭据
- 怎么换版本：`git pull`
- 发坏了怎么退：`git checkout` 上一提交
- 按 PRD「不做」：不建设商业分发与自动更新机制
