# 架构：网盘自动上传

> 阶段 1 为 CLI + 本地监控（无图形界面）；**阶段 2 起有前端**——本地 Web 管理台（浏览器访问，F4）：前端代码组织见 `FRONTEND.md`，界面结构与视觉约定见 `DESIGN_SYSTEM.md`。桌面端仍在「后续阶段」。

## 1. 数据流

```
本地文件（三种入口）
  ├─ CLI 手动指定（F1；一次可指定多个网盘，各自目录）
  ├─ watcher 监控目录新文件（F2；阶段 2 起监控根的「网盘@远端目录」约定文件夹自动成为规则，F5）
  └─ Web 管理台手动上传（F4，阶段 2；网盘多选 + 每盘目录 + 标题）
          │
          ▼
core 上传任务（publish_task）：一个文件 → 按网盘逐个跑单盘管道（去重 → 建目录 → 分片上传 → 创建分享）
          │                                   │
          │                                   ├─► 台账（SQLite）：每个「文件 × 网盘」一行，同任务共享 group_id
          │                                   ▼
          │                         任务聚合：文件 + 各盘链接 + 失败项
          │                                   │
          │                                   ├─► writer（飞书）：最顶插入**一节**（h2「YYMMDD 标题名」+ 成功盘各一行）
          │                                   └─► 待修列表：失败项留台账，页面与 CLI 可重试
          ▼
输出：CLI 打印各盘链接 / watch 日志 / Web 页面展示链接与记录
```

一句话：本地文件经上传任务分发到一个或多个网盘的指定目录并生成分享链接，一个任务的链接合并写入飞书文档一节，全过程记入本地台账；阶段 2 起浏览网页即完成上传、记录查看、待修重试与监控管理。

现状与目标的差距：阶段 1 的 I-001 ～ I-006 代码已完成并全部验收；阶段 2 差距 = Web 服务与 SPA、目录约定解析，对应看板 B2（I-007 ～ I-010）；另有「一次上传多盘」的任务层（F1/F3 修订，I-015 / I-016）尚未落地，落地前 `publish_file` 仍是单盘单写文档。

## 2. 模块分类与依赖方向

分类框架：**接入层**（网盘、文档写入）/ **核心**（管道、台账、配置）/ **入口**（CLI、watcher；未来的 Web、桌面、MCP）。

| 模块 | 在数据流中的职责 | 代码目录 | 允许依赖 | 禁止依赖 |
|---|---|---|---|---|
| drivers | 网盘客户端：登录态校验、建目录、上传、创建分享 | `src/panup/drivers/` | config | core、writers、入口 |
| writers | 文档写入端：向指定文档追加记录 | `src/panup/writers/` | config | core、drivers、入口 |
| core | 上传任务编排（一个文件分发到多个网盘）、单盘上传管道、去重、台账、驱动与写入端注册表 | `src/panup/core/` | drivers、writers、config | 入口 |
| cli | 命令入口：upload / status / watch / serve 转发 | `src/panup/cli.py` | core | drivers、writers |
| watcher | 目录监控，产出新文件事件交给 core；阶段 2 支持约定目录动态规则 | `src/panup/watcher.py` | core | drivers、writers |
| web | 本地管理台服务端（FastAPI REST API + 托管 SPA 静态资源） | `src/panup/web/` | core、watcher | drivers、writers |
| config | 配置与密钥加载、启动校验 | `src/panup/config.py` | — | — |

依赖方向：入口（cli / watcher / web）→ core → drivers / writers → config，单向；drivers 内部、drivers 与 writers 之间互不依赖。

通信契约按「未来会新增」设计：新增一个网盘 = `drivers/` 下新增一个驱动文件并在注册表登记一行；新增一个写入目标 = `writers/` 下新增一个文件并登记；新增一个入口（桌面 / MCP）= 调 core 公开函数或 REST API，不改 core；Web 前端只消费 REST API（`/api/*`），不 import 服务端内部。

技术栈：

- **Python 3.13 标准库优先**（已验证的零依赖实现可照搬）：`urllib` 解决 HTTP 调用，`sqlite3` 解决台账存储，`tomllib` 解决配置读取，`argparse` 解决 CLI，`logging` + 手写 JSON lines 解决日志。适用：个人本机工具、装机门槛低；不适用：当出现需要并发框架或异步 I/O 的需求时（后续阶段再评估）；风险：无第三方生态兜底，接口层改动需自己维护。
- **飞书开放平台 docx API 直调**：官方文档明确、个人自建应用可用。适用：向既有文档追加块；不适用：批量管理整个云空间时（权限模型不同）；风险：接口限频（个位数次/秒），串行调用即可。
- **Web 服务端 FastAPI + uvicorn（阶段 2，人选定）**：解决「管理台 REST API + 文件流式上传」。适用：本地单用户管理台、需要自动接口文档与校验时；不适用：当需要分发给他人部署时（会引入配置与安全面）；风险：引入两个第三方依赖（打破零依赖，AGENTS §11 条款 2 已随之修订），升级依赖时锁版本。前端为免构建 SPA 静态资源（原生 HTML/JS/CSS），由 FastAPI 托管，不引入 Node 构建链。被否决：标准库 http.server（multipart 流式解析与异步转发自造成本高于两个依赖）；Flask（无原生异步与校验，优势不再）。
- **目录监控用标准库轮询起步**（间隔可配，默认 5 秒）：零依赖；若轮询不满足再评估引入 `watchdog`（引入前须在 issue 里说明理由并更新本节）。
- 被否决的候选见第 4 节。

核心实体与关系：一次**上传任务**（一个本地文件 + 人给的标题 + 若干「网盘 × 目录」）产生 N 条**上传记录**（文件、某网盘、远端路径、分享链接、提取码、状态），记录共享 `group_id` 指向同一任务；表结构与字段 → BACKEND。

## 3. 架构级红线（约束）

按主题分组，每条同行写「怎么检查」：

**模块边界**

- **AC-01** 入口（cli / watcher）不得直接 import drivers / writers，一律经 core ｜ 检查：评审核对 import 方向
- **AC-02** 新增网盘或写入目标只新增注册文件与注册表一行，不改既有模块 ｜ 检查：评审新增驱动的 diff，应只含新文件 + 注册表一行
- **AC-03** 网盘与文档接口的响应解析只发生在 drivers / writers 内部，core 只消费契约返回值 ｜ 检查：评审时确认 core 无网盘端点常量

**安全边界**

- **AC-04** 凭据（网盘 cookie、飞书 app secret）只存 `secrets/` 或环境变量，不进仓库、不进日志 ｜ 检查：`git status` 不出现 secrets；日志文件中 grep 不到 cookie 值与提取码
- **AC-05** 日志与台账不得记录 cookie、secret 明文 ｜ 检查：评审日志字段清单 + 抽查日志文件

**失败可见**

- **AC-06** 驱动与写入端失败必须显式报错（含 errno / 错误码与恢复指引），不得用默认值、空返回或静默重试把失败伪装成成功 ｜ 检查：验收时人为使 cookie 失效，确认报错文案与退出码
- **AC-07** 监控上传必须去重：同一文件（路径 + 内容指纹）不重复上传，重启后依然 ｜ 检查：验收时放入同一文件两次并重启监控，台账只有一条成功记录

**风险边界**

- **AC-08** cookie 方案的操作保持低频串行（批量场景逐文件间隔 ≥ 1 秒），不做高频并发，降低风控风险 ｜ 检查：评审批量路径代码无并发上传调用

项目私有规则：以上全部为本项目私有约束，不与其他项目共用。

## 4. 关键选择的理由

- **网盘接入走 cookie 网页版接口**：分享链接个人可创建，接口流程已在本地实测可用（2026-11，百度上传 + 分享全链路验证通过）。否决官方开放平台 OAuth（分享 / 上传接口需企业认证主体，个人申请不下来；且多一套 token 刷新与回调基建）。风险：cookie 会失效、有风控可能，恢复方式 = 重新登录导出 cookie；接口改版可能失效，靠错误显式暴露（AC-06）而非静默。
- **驱动抽象对齐 alist 的 Driver 设计（裁剪子集）**：alist 的网盘驱动接口成熟稳定，新增网盘照其流程移植，不重新发明接口语义。否决每个网盘自造一套方法名（扩展时接口漂移，上层要跟着改）。
- **核心与入口彻底分离**：CLI 与 watcher 是第一层薄壳；Web 端、桌面端、MCP server（后续阶段）共用同一 core，新增入口不改核心。否决把业务逻辑写进 CLI（未来每个入口都要重写一遍）。
- **台账用 SQLite 单文件**：去重（AC-07）与失败记录需要条件查询和唯一索引。否决 JSON 文件（并发写与按指纹查询都要自己造）。
- **标准库优先、零第三方依赖起步**：已验证的零依赖实现证明可行，装机门槛最低。否决起步就引入 requests / fastapi（阶段 1 没有任何一个 issue 需要它们；出现需求时按第 2 节的适用条件评估）。
- **飞书先行、腾讯文档列后续阶段**：飞书官方 docx API 个人自建应用即可用；腾讯文档开放平台的在线文档写入权限门槛高。否决先做腾讯文档（会阻塞 F3）。
- **轮询监控起步**：零依赖够用；否决起步即引入 watchdog（个人目录监控频率低，暂无 issue 需要）。

## 5. 可观测性总览

- 档位：本地小工具
- 日志去向与查询入口：JSON lines 落 `logs/` 按天滚动，一条 grep 命令查询（字段、事件目录、保留与脱敏 → BACKEND「日志、指标与告警」）
- 事件 / 错误码目录：由 BACKEND 定义（`core/errors.py` 常量表 + 文档；执行期建）

## 6. 交付与升级

- 分发形态：只在本人的机器上运行（自用工具）
- 制品怎么到用户手里：不适用——本机 git 仓库即制品；换机器时 clone + 按 BACKEND「配置与密钥」重新配置凭据
- 怎么换版本：`git pull`
- 发坏了怎么退：`git checkout` 上一提交
- 按 PRD「不做」：不建设商业分发与自动更新机制
